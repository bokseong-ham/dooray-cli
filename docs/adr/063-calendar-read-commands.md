## ADR-063: 캘린더는 읽기 세 명령만 두고 기간은 항상 양끝을 보낸다

**결정**: `calendar list` 와 `calendar event list` 와 `calendar event get` 셋을 둔다.
일정 생성·수정·삭제는 두지 않는다.
`event list` 는 `--from` 과 `--to` 를 받아 **언제나 `timeMin` 과 `timeMax` 를 함께** 보낸다.

| 명령 | endpoint | 공식 문서 |
| --- | --- | --- |
| `calendar list` | `GET /calendar/v1/calendars` | 있다 |
| `calendar event list` | `GET /calendar/v1/calendars/*/events` | **없다** |
| `calendar event get` | `GET /calendar/v1/calendars/{calendar-id}/events/{event-id}` | 있다 |

**맥락**: 캘린더를 다루는 명령이 없었다. 회의 참석 여부를 확인하거나 기간 안의 일정을 모으는 일은
CLI 밖에서 따로 스크립트를 짜야 했다.

**실측으로 확인한 것**:

응답 형태와 파라미터 동작은 실제 호출로 확인했다.

- **목록은 참석자를 주지 않는다.** `users` 키는 오지만 `from` 과 `to` 와 `cc` 가 모두 `null` 이다.
  `calendar` 도 `{ id, name }` 뿐이다. 참석 여부를 알려면 상세를 따로 열어야 한다.
- **상세에는 이름이 들어 있다.** `users.from` 은 객체 하나, `to` 와 `cc` 는 배열이고
  각 항목이 `{ type, status, member: { organizationMemberId, name, emailAddress } }` 다.
  그래서 `messenger logs` 와 달리 멤버를 따로 조회하지 않는다.
- **상세는 calendarId 자리에 `*` 를 받지 않는다.** `SERVER_GENERAL_ERROR` 가 난다. 두 id 가 모두 필요하다.
- `timeMin` 과 `timeMax` 는 동작한다. `size` 와 `page` 는 무시된다.
- **`timeMin` 만 준 결과가 아무 파라미터도 주지 않은 것과 같았다.** 한쪽만으로는 범위를 좁히지 못하는 것으로 보인다.
- **잘못된 날짜 형식에 서버가 500 을 낸다.** `timeMin=2026-09-20` 처럼 offset 없는 값을 주면
  `Server error occurred. Please contact help@dooray.com` 이 온다. 서버에 형식 검증이 없다.

**종일 일정은 형식과 종료 해석이 모두 다르다**:

```
종일  startedAt: 2026-09-18+09:00          (T 시각이 없다)
종일  endedAt  : 2026-09-19+09:00
일반  startedAt: 2026-09-15T16:00:00+09:00
일반  endedAt  : 2026-09-15T17:00:00+09:00
```

`endedAt` 은 **그 날을 포함하지 않는다.** 위 일정을 날짜별로 조회해 확인했다.

| 조회 범위 | 그 일정이 잡히는가 |
| --- | --- |
| `2026-09-17` | 안 잡힌다 |
| `2026-09-18` | **잡힌다** |
| `2026-09-19` | 안 잡힌다 |

`endedAt` 이 `09-19` 인데 09-19 조회에 걸리지 않으므로, 이 일정의 실제 마지막 날은 `09-18` 하루다.
따라서 화면에 그릴 마지막 날은 `endedAt - 1일` 이다.

**공식 문서에 없는 endpoint 다 (`event list` 만)**:

저장소의 공식 endpoint 스냅샷(`docs/api/official-endpoints.txt`)에 캘린더 경로가 11개 있는데
`GET /calendar/v1/calendars/{calendar-id}/events` 만 없다. 같은 경로의 `POST`(생성)와
하위의 `GET .../events/{event-id}`(상세)는 실려 있다.

**ADR-062 의 조건 1(공식 문서를 화면으로 열어 확인)은 아직 채우지 못했다.**
공식 문서가 React 앱이라 이 환경에서 열리지 않아 스냅샷 대조까지만 했다.
조건 2(실측)와 4(README·SKILL·`--help` 경고)는 채웠다.

조건 3(`KNOWN_UNDOCUMENTED` 등록)은 **조건 1 을 채우지 않은 채로 등록했다.**
그 목록의 주석은 "확인하지 않은 것을 여기 넣으면 스냅샷이 낡아서 생긴 차이가 묻힌다" 고 막고 있고,
ADR-062 는 네 조건을 모두 채워야 쓸 수 있다고 정한다. 그래서 이것은 정책을 벗어난 상태다.

등록을 미루는 쪽(스크립트가 1건을 계속 올리게 두는 것)은 ADR-062 가 이미 기각한 안이라 택하지 않았다.
대신 **사유에 「화면 확인 미완」 을 적어** 목록 안에서 구분되게 했다.
이 표기가 맞는지, 아니면 ADR-062 에 "조건 1 미충족 상태로 등록할 때의 표기" 를 절로 넣어야 하는지는
이 저장소의 정책을 소유한 쪽이 정할 일이라 여기서 결정하지 않는다.

화면 확인이 끝나면 이 절과 `KNOWN_UNDOCUMENTED` 의 사유를 그 결과로 바꾼다.

`calendar list` 와 `event get` 은 문서에 있으므로 경고 대상이 아니다.

**설계 결정**:

- **기간은 항상 양끝을 보낸다.** 한쪽만 주면 서버가 범위를 좁히지 않으므로,
  둘 다 없으면 오늘 하루로 잡고 한쪽만 주면 나머지를 오늘 기준으로 채운다.
  사용자가 준 범위와 실제로 조회된 범위가 어긋나지 않게 하는 것이 목적이다.
- **날짜 형식은 CLI 가 막는다.** `YYYY-MM-DD` 와 offset 이 붙은 ISO8601 만 받고,
  날짜만 주면 그 날짜의 로컬 offset 으로 `00:00:00` 과 `23:59:59` 로 넓힌다.
  offset 없는 일시(`2026-09-20T09:00:00`)는 거부한다. 서버가 500 을 내는 입력을 네트워크 앞에서 잘라낸다.
  offset 은 고정값이 아니라 **그 날짜의** 것을 쓴다. 서머타임이 있는 지역에서 오늘 offset 을
  다른 날짜에 붙이면 한 시간 어긋난 범위를 보내게 된다.
- **시각은 `Date` 로 파싱하지 않는다** (ADR-061 과 같은 이유). `+09:00` 일 때만 offset 을 떼고
  그 밖의 offset 이나 `Z` 는 원형을 보여준다. 종일 일정은 날짜만 오는 별도 형식이라 파서를 나눈다.
- **종일 일정은 기간으로 그린다.** 하루면 `2026-09-18 (종일)`, 여러 날이면
  `2026-09-18 ~ 2026-09-20 (종일)` 이다. 마지막 날은 `endedAt - 1일` 로 구하되
  날짜 문자열을 UTC 자정으로 세워 빼고 다시 문자열로 되돌린다. 지역 시간대를 거치지 않는다.
  데이터가 어긋나 마지막 날이 시작보다 앞서면 기간을 그리지 않고 시작 날짜만 낸다.

**대안 기각**:

- **일정 생성·수정·삭제까지 제공** — 목록 endpoint 가 문서에 없는 상태에서 쓰기까지 넓히면
  ADR-062 가 정한 "문서에 없는 경로는 읽기 전용" 을 벗어난다. 생성과 수정은 문서에 있으나
  이번 범위를 읽기로 맞춘다.
- **한쪽만 준 기간을 그대로 보내기** — 서버가 그 값을 무시하므로 사용자가 지정한 범위와
  실제 조회 범위가 달라진다. 결과만 보고는 알아챌 수 없다.
- **잘못된 날짜를 서버에 맡기기** — 500 과 `help@dooray.com` 안내가 돌아온다.
  입력 실수인데 서버 장애처럼 보인다.
- **종일 일정을 시작 날짜만 표시** — `endedAt` 이 exclusive 라는 것을 확인하기 전의 방식이다.
  장기 일정이 하루짜리로 보여 오독을 부른다.
- **상세에서도 멤버를 따로 조회** — 상세 응답에 이름이 이미 들어 있어 불필요하다.
