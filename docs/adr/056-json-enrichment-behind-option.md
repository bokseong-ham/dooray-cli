## ADR-056: `--json` 의 raw 유지는 그대로 두고, 이름 보강은 별도 옵션으로 연다

- **status**: `accepted`

- **결정**: `--json` 은 서버 응답을 그대로 내는 기본을 유지한다.
  보강한 값이 필요한 호출은 `--with-tag-names` 처럼 보강을 명시하는 옵션을 준다.
  `post get --with-tag-names` 는 `tags[]` 의 각 항목에 `name` 을 더한다.

  이름을 찾지 못한 태그에는 `name` 키를 **넣지 않는다.** 빈 문자열로 채우면 이름이 비어 있는 태그와 구별되지 않는다.
  하나라도 채우지 못하면 종료 코드 `EXIT_API_ERROR` 로 끝내고 어느 태그인지 stderr 에 적는다.
  옵션을 준 호출은 이름을 기대하므로, 조용히 일부만 채우면 호출하는 쪽이 그 사실을 알 수 없다.

  일반 출력(표와 산문)의 보강은 이 결정의 대상이 아니다. ADR-021 이 정한 대로 계속 보강한다.
  `post get` 의 일반 출력에 `태그:` 줄을 더하는 것이 여기 해당한다.

- **대체된 부분**: 없다. [ADR-021](021-member-command-creator-enrich.md) 과
  [ADR-043](043-wiki-name-search-and-project-column.md) 의 raw 유지 결정을 그대로 둔 채,
  그 결정이 다루지 않은 「명시적으로 보강을 요청한 호출」을 더한다.

- **맥락**: 이슈의 보고는 「`post get --json` 이 최상위 키 둘만 돌려준다」였다.
  코드를 읽어 보니 그렇지 않았다. `src/commands/post/get.ts` 가 `getPost()` 의 `res.result` 를
  그대로 `formatPostDetail` 에 넘기고, 그 포맷터는 `--json` 이면 응답 전체를 낸다.
  실제 계정으로 확인한 응답도 최상위 키가 18 개였다.
  실제 문제는 응답의 `tags[]` 가 `id` 만 담는 것이었다.
  같은 보고가 다시 와도 이 조사를 반복하지 않도록 여기 적어 둔다.

  업무에 태그를 붙인 뒤 들어갔는지 확인할 수단이 CLI 에 없었다.
  응답의 `tags[]` 는 `{"id": "..."}` 만 담고 이름이 없다.
  이름을 알려면 프로젝트 태그 목록을 따로 받아 ID 를 맞춰야 하고, 실제로 사용자들이 그 대조를 직접 만들어 쓰고 있었다.
  `post get` 의 일반 출력에는 태그가 아예 나오지 않았다.

  응답에 이름을 항상 채우는 안은 ADR-021 과 ADR-043 이 이미 기각했다.
  기각 근거는 외부 도구 호환성이고, 그 근거는 지금도 유효하다.

  항상 채우면 문제가 하나 더 생긴다.
  캐시가 오래돼 이름을 못 찾은 것과 목록 조회가 실패해 못 찾은 것이 출력에서 같아 보인다.
  자동화가 그 둘을 구별할 수 없다. 옵션으로 두면 옵션을 준 호출에서만 종료 코드로 구별할 수 있다.

- **대안 기각**:
  - **`--json` 에 항상 `name` 을 더한다** — ADR-021 과 ADR-043 이 같은 모양을 기각한 근거가 그대로 남는다.
    보강 실패를 종료 코드로 알리면 지금 raw 만 읽던 호출까지 실패하게 되고,
    알리지 않으면 캐시가 오래된 것과 조회가 실패한 것을 구별할 수 없다.
  - **일반 출력에만 태그 줄을 더하고 `--json` 은 건드리지 않는다** — 자동화가 태그 이름을 얻을 방법이 없다.
    이슈가 보고한 우회(REST API 직접 호출)가 그대로 남는다.
  - **태그 이름을 담은 별도 명령을 만든다** — `project tags` 가 이미 목록을 낸다.
    필요한 것은 목록이 아니라 그 업무에 붙은 태그의 이름이라, 명령을 나누면 대조를 호출하는 쪽에 그대로 남긴다.
  - **보강 범위를 `post list` 까지 넓힌다** — 이슈가 요구한 것은 붙인 태그의 확인이다.
    목록에서 태그로 찾는 요구는 `post list --tag` 필터가 직접 담는다. 보강과 필터는 다른 요구다.
  - **`post list` 의 표에 태그 열을 더한다** — 그 표는 이미 다섯 열이고,
    태그는 업무마다 개수가 달라 열 폭이 다른 열보다 불규칙하다.
    좁은 터미널에서 줄이 접히는 것을 [ADR-043](043-wiki-name-search-and-project-column.md) 이
    감당할 것으로 적었는데, 태그 열은 그 폭이 더 커진다.
    목록에서 태그로 찾는 요구는 `post list --tag` 필터가 직접 담는다.

- **결과**:
  - 얻는 것: 태그를 붙인 뒤 `post get --json --with-tag-names` 한 번으로 확인할 수 있다.
    옵션을 주지 않은 호출의 출력은 달라지지 않아 기존 자동화가 그대로 동작한다.
    사람이 읽는 출력에는 항상 태그가 보인다.
  - 감당할 것: 옵션을 준 호출마다 프로젝트 태그 목록 조회가 붙는다.
    태그 캐시가 있어 기간 안에는 한 번이지만, 캐시를 채운 뒤에 만든 태그는 이름을 찾지 못해 그 호출이 실패한다.
    `--with-tag-names` 라는 이름이 태그에 묶여 있어, 다른 값을 보강할 때는 옵션을 따로 더해야 한다.

- **적용 범위**: `src/commands/post/get.ts`, `src/formatters/post.ts`, `src/resolvers/tag.ts`.
  `post list --tag` 필터는 이 결정과 별개이며 기존 `tagIds` 질의 인자를 그대로 쓴다.
  `tagIds` 에 여러 값을 보냈을 때의 해석은 공식 문서가 정의하지 않는다.
  같은 문서가 `postWorkflowClasses={},{}` 처럼 쉼표 형태를 적는 인자와 달리 `tagIds={tagId}` 로만 적는다.
  실제 호출로 확인한 결과 둘을 함께 보내면 둘 다 가진 업무만 온다.
  태그 A 가 421 건, 태그 B 가 91 건인 프로젝트에서 둘을 함께 보내면 23 건이 오고,
  그 23 건의 상세를 모두 받아 확인하니 전부 두 태그를 가지고 있었다.
