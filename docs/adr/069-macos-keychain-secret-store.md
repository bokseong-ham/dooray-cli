## ADR-069: macOS 에서는 `apiKey` 와 `imapPassword` 를 로그인 키체인에 둔다

**결정**: macOS 에서 `apiKey` 와 `imapPassword` 를 `~/.dooray/config.json` 이 아니라 로그인 키체인에 저장한다.
service 는 `dooray-cli`, account 는 필드 이름(`apiKey`, `imapPassword`)이다.
옵트인 설정 없이 기본으로 쓴다. macOS 가 아닌 OS 는 지금처럼 config.json 에 0600 평문으로 저장한다.

- 비밀 저장소는 `src/config/secret-store.ts` 의 `SecretStore` 인터페이스(`get`·`set`·`delete`) 뒤에 둔다.
  `getSecretStore()` 가 macOS 에서 키체인 구현을, 그 밖에서 `null` 을 돌려준다.
  Linux·Windows 백엔드는 이 인터페이스를 구현해 붙인다.
- 호출부는 바꾸지 않는다. `src/config/store.ts` 의 `getConfig`·`saveConfig`·`setConfigValue`·`clearMailCredentials` 가
  저장 위치를 감춘다.
- 키체인은 네이티브 모듈 없이 `/usr/bin/security` 를 절대경로로, shell 없이 띄워 다룬다.

**ADR-007 과의 관계**: ADR-007 의 「환경변수로 받지 않는다」 는 그대로다.
이번 결정은 저장 위치만 넓힌다. 값을 넣는 경로는 여전히 `dooray setup` 과 `dooray config set` 이고,
`config set <key> -` 의 stdin 경로도 그대로 쓴다.

**맥락**: config.json 은 0600 으로 저장하지만(`docs/pitfalls/code-review/sensitive-file-mode-missing.md`)
같은 사용자 권한으로 도는 모든 프로세스가 읽을 수 있다. 백업, dotfiles 동기화, 실수로 붙여 넣는 설정 덤프에도 평문 토큰이 따라간다.
키체인은 그 사용자의 로그인 세션 밖에서는 잠겨 있고, 다른 앱이 읽으려 하면 접근 허용을 묻는다.

**실측으로 확인한 것** (macOS, 더미 값):

- **`add-generic-password ... -w` 를 값 없이 주고 stdin 으로 넘기면 멈춘다.** tty 가 붙은 프로세스에서는
  stdin 이 아니라 `/dev/tty` 에서 비밀번호를 읽으려고 기다린다. 사용자가 터미널에서 CLI 를 띄우는 것이 기본이라 쓸 수 없다.
- **`add-generic-password ... -w <값>` 은 값이 argv 에 남는다.** 실행 중에 `ps` 로 보인다.
  이 저장소는 같은 노출을 피하려고 `config set <key> -` stdin 경로를 따로 두었다. 같은 구멍을 다시 열 수 없다.
- **`security -i` 의 stdin 으로 명령 한 줄을 넘기면 tty 가 있어도 멈추지 않고 저장된다.** 넘기는 줄은
  `add-generic-password -U -s dooray-cli -a <field> -w "<escaped>"` 이다.
  큰따옴표 안에서 `\` 를 `\\` 로, `"` 를 `\"` 로 바꾸면 `a b"c\d$e'f` 가 그대로 복원됐다.
  stdin 이 tty 가 아니면 stdout 에 프롬프트가 찍히지 않았다. 이 방식을 쓴다.
- **`find-generic-password -w` 는 출력할 수 없는 바이트가 있는 값을 hex 로 출력한다.**
  원래 값이 우연히 hex 문자열인 경우와 구별할 수 없다. 줄바꿈은 `-i` 로 넘기는 명령 한 줄을 끊는다.
- **항목이 없으면 종료 코드 44 다.** `find-generic-password` 와 `delete-generic-password` 모두 그렇고,
  `-i` 모드도 안의 명령이 항목을 못 찾으면 44 를 돌려줬다.
  `-i` 에서 `add-generic-password` 가 실패할 때의 종료 코드는 확인하지 못했다. 0 이 아니면 실패로 본다.
- **`find-generic-password -w` 의 출력은 값 뒤에 개행 하나가 붙는다.** 그 하나만 뗀다. `trim` 은 값 앞뒤 공백을 지우므로 쓰지 않는다.
- **`security` 는 로그인 키체인을 `$HOME/Library/Keychains` 에서 찾는다.** `HOME` 을 다른 경로로 두면
  `default-keychain` 이 「A default keychain could not be found」 로 실패하고, 쓰기에서는 macOS 가
  키체인을 찾을 수 없으니 기본값으로 재설정하겠느냐는 대화상자를 띄웠다. 그 버튼은 실제 로그인 키체인을 초기화할 수 있다.
  `HOME` 에 `os.userInfo().homedir`(계정 정보의 홈)를 넣으면 실제 로그인 키체인을 찾았다.
  그래서 `security` 를 띄울 때는 `HOME` 만 계정의 실제 홈으로 바꿔 넘긴다. config.json 의 위치는 지금처럼 `HOME` 을 따른다.

**설계 결정**:

- **비밀값은 출력 가능한 ASCII(0x20-0x7E)만 받는다.** 위 hex 출력과 줄바꿈 문제 때문이다.
  사용자가 새로 준 값에 그 밖의 문자가 있으면 키체인에도 파일에도 쓰기 전에 `EXIT_PARAM_ERROR`(3)로 거절한다.
  파일에 있던 구버전 값은 예외다. 아래 「새로 준 값과 파일에 있던 값」 항목을 본다.
  거절 메시지에는 필드 이름만 넣고 값은 넣지 않는다. Dooray API 토큰과 메일 앱 비밀번호는 이 범위 안이라 실사용에 걸리지 않는다.
  macOS 가 아닌 OS 는 이 검사를 하지 않는다. 파일 평문 저장에는 같은 제약이 없어 기존 동작을 바꿀 이유가 없다.
- **읽을 때는 필드마다 파일 값이 앞선다.** config.json 에 비어 있지 않은 값이 있으면 그 값을 쓰고 키체인은 읽지 않는다.
  필드가 없거나 빈 문자열일 때만 키체인을 읽고, 둘 다 없으면 미설정이다.
  새 CLI 는 저장에 성공하면 언제나 파일에서 비밀 필드를 뺀다. 그러므로 파일에 평문이 남아 있으면
  아직 옮기지 않은 구버전 값이거나, 다운그레이드한 구버전 CLI 가 나중에 쓴 값이다. 둘 다 파일이 맞다.
  저장이 중간에 실패해 파일이 그대로 남은 경우에도 「저장 실패는 옛 설정 유지」 라는 뜻이 된다.
  파일에 값이 있는 필드는 `security` 를 띄우지 않는다. `dooray-persona` 스크립트도 같은 규칙이다.
- **마이그레이션은 저장할 때 일어난다.** `setup`, `config set`, `mail logout` 처럼 설정을 저장하는 순간
  비밀값을 키체인에 쓰고 config.json 에서 그 필드를 뺀다.
  `config set track-last-run true` 처럼 비밀값과 무관한 키를 저장해도 옮겨진다.
  별도 migrate 명령은 두지 않는다. 읽기만 하는 명령이 파일을 고치는 부작용도 두지 않는다.
- **저장할 때는 바뀐 필드만 키체인에 쓴다.** 저장 직전에 config.json 을 다시 읽고, 키체인의 현재 값과 필드마다 비교한다.
  - 새 값이 비었거나 없으면 키체인에 있던 항목을 지우고 파일에서도 뺀다. `clearMailCredentials` 가 이 경로로 `imapPassword` 를 지운다.
  - 새 값이 키체인의 현재 값과 같으면 키체인을 건드리지 않는다. `config set tenant-name` 이 `apiKey` 를 다시 쓰지 않는다.
  - 그 밖에는 키체인에 쓰고 파일에서 뺀다. 파일의 구버전 값을 옮기는 경우도 여기에 든다.
- **사용자가 새로 준 값과 파일에 있던 값을 다르게 검증한다.** 새로 준 값이 출력 가능한 ASCII 가 아니면
  어느 쪽에도 쓰기 전에 거절한다. 파일에 있던 구버전 값이 그렇다면 거절하지 않는다.
  그 필드는 파일에 평문으로 남기고, 키체인에 옮기지 못했고 값을 바꾸면 옮겨진다는 경고를 stderr 로 한 번 낸다. 경고에 값은 넣지 않는다.
  거절하면 그 필드와 무관한 `config set base-url` 까지 막혀 사용자가 설정을 고칠 길이 없어진다.
  「파일에 있던 값」 은 저장 직전에 읽은 파일 값과 새 값이 같은 경우로 가린다.
- **키체인에 먼저 쓰고 파일을 쓴다. 뒤 단계가 실패하면 이번 저장에서 바꾼 키체인 항목을 되돌린다.**
  키체인 쓰기 도중이나 파일 쓰기에서 실패하면, 이미 바꾼 필드를 역순으로 이전 값으로 다시 쓴다. 이전에 없던 필드는 지운다.
  config.json 은 tmp 와 rename 으로 쓰므로 실패하면 이전 파일이 그대로 남는다. 둘을 합쳐 「저장 실패는 옛 설정 유지」 가 된다.
  되돌리기는 best-effort 다. 키체인이 그 사이에 잠기면 되돌리기도 실패할 수 있다.
  그때는 원래 오류의 종료 코드를 유지하고, 메시지에 「키체인 일부가 새 값으로 남았을 수 있다」 와 해당 필드 이름을 덧붙인다.
  남은 새 값은 파일에 같은 필드의 평문이 있으면 읽기 우선순위 때문에 쓰이지 않는다.
- **config.json 이 없으면 키체인을 보지 않고 `absent` 다.** 설정 파일이 설정의 존재를 정한다.
- **같은 프로세스 안에서는 키체인 값을 기억한다.** `config set` 은 한 번에 `getConfig` 를 세 번 부른다.
  키체인 구현 인스턴스가 읽은 값과 쓴 값을 기억하고, 쓰기와 지우기가 성공하면 그 값으로 바꾼다. 실패는 기억하지 않는다.
  되돌리기도 같은 `set`·`delete` 를 거치므로 되돌린 뒤의 기억도 실제 상태와 맞는다. 되돌리기에 실패한 필드는 기억에서 빠져 다음 읽기가 키체인을 다시 본다.
  인스턴스는 프로세스마다 새로 생기므로 다른 프로세스가 바꾼 값을 놓치는 기간은 명령 한 번이다.
- **오류 메시지에 비밀값을 넣지 않는다.** `security` 의 stderr 를 옮길 때 값과 이스케이프한 값을 `***` 로 가린다.
- **`dooray-persona` 스킬 스크립트도 같은 항목을 읽는다.** 파일에 `apiKey` 가 없거나 비었을 때만
  `find-generic-password` 로 읽는다. 읽기는 argv 에 비밀값이 없다.

**테스트**: 실행 OS 에 따라 실제 키체인을 건드리지 않게 한다.
기존 `store.test.ts`·`store.fs.test.ts` 는 `secret-store.js` 를 mock 해 `getSecretStore` 를 `null`(파일 모드)로 고정한다.
키체인 모드는 `store.keychain.test.ts` 가 가짜 `SecretStore` 를 넣어 보고, 키체인 구현은 `secret-store.test.ts` 가
`node:child_process` 를 mock 해 본다. RETRO-0017 처럼 store 가 직접 부르는 모듈을 이름으로 mock 한다.

**대안 기각**:

- **keytar, @napi-rs/keyring 같은 네이티브 모듈** — tsup 단일 CJS 번들에 네이티브 바이너리를 넣을 수 없다.
  플랫폼별 prebuild 를 따로 배포해야 하고 설치 실패 경로가 생긴다.
- **옵트인 설정으로 켜기** — 켜지 않은 사용자는 그대로 평문이다. 보안 기본값을 사용자가 찾아 켜야 하는 형태가 된다.
- **키체인 값을 파일 값보다 앞세우기** — 처음 구현이 이랬다. 다운그레이드한 구버전 CLI 가 파일에 새 토큰을 써도
  키체인의 낡은 토큰이 이긴다. 키체인 쓰기 뒤 파일 쓰기가 실패하면 파일은 옛 값인데 키체인 새 값이 읽혀 「저장 실패」 가 반쯤 반영된다.
  파일에 값이 있어도 매번 `security` 를 띄운다.
- **모든 저장에서 비밀 필드를 다시 쓰기** — 바뀌지 않은 값마다 `security` 를 띄우고, 그만큼 되돌릴 대상도 늘어난다.
- **파일의 비ASCII 구버전 값도 거절** — 그 필드와 무관한 저장까지 막혀 설정을 고칠 수 없다.
- **별도 `config migrate` 명령** — 사용자가 알아야 실행한다. 저장 시점 이동이면 다음 `config set` 이나 `setup` 에 저절로 옮겨진다.
- **읽을 때 옮기기** — `post list` 같은 조회 명령이 설정 파일을 고치게 된다. 읽기 명령의 부작용은 두지 않는다.
- **비 macOS 에도 ASCII 검사** — 지금 평문 저장에 제약이 없고, 그 OS 의 백엔드가 생길 때 그 백엔드의 제약에 맞춰 정한다.

**결과**:

- 얻는 것: macOS 에서 config.json 을 읽어도 토큰과 메일 비밀번호가 나오지 않는다.
  키체인이 잠긴 세션에서는 비밀값을 읽을 수 없다.
- 감당할 것: 파일에 비밀값이 없는 명령마다 읽기용 `security` 를 최대 두 번 띄운다. 처음 읽을 때 키체인 접근 허용을 묻는 창이 뜰 수 있다.
  키체인으로 옮긴 뒤 이전 버전 CLI 로 돌아가면 config.json 에 `apiKey` 가 없어 손상으로 판정된다. 그때는 `dooray setup` 을 다시 한다.
  비ASCII 비밀값은 macOS 에서 새로 저장할 수 없다. 구버전이 남긴 비ASCII 값은 config.json 에 평문으로 남는다.
  되돌리기가 실패하면 키체인 일부가 새 값으로 남을 수 있다.

**후속 과제**:

- **`getConfig` 가 필요 없는 `imapPassword` 까지 읽는다.** 메일과 무관한 `post list` 도 `imapPassword` 를 키체인에서 읽고,
  그 읽기가 실패하면 `unreadable` 이 되어 명령이 막힌다. 필드를 쓸 때 읽는 지연 읽기가 맞지만,
  메일 클라이언트가 `Config` 를 동기 객체로 받아 쓰는 부분까지 바꿔야 해서 이번 범위에서 뺐다.
- **`src/index.ts` 의 전역 오류 처리가 `trackLastRun` 을 보려고 `getConfig` 를 다시 부른다.** 같은 프로세스 안이라 키체인 값은
  기억에서 나오지만, 앞선 읽기가 실패했으면 키체인을 한 번 더 띄운다. 비밀 필드가 필요 없는 읽기 경로를 따로 두면 없앨 수 있다.
