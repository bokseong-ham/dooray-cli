## ADR-057: `download-all` 은 첨부 목록과 본문에 삽입된 파일을 함께 받는다

- **status**: `accepted`

- **결정**: `post file download-all` 이 첨부 목록과 본문의 `/files/<id>` 참조를 합쳐 대상으로 삼는다.
  두 곳에 같은 id 가 있으면 한 번만 받는다.
  본문의 파일을 제외하려면 `--no-inline` 을 준다.

  받을 것이 하나도 없으면 종전대로 `첨부파일이 없습니다` 를 낸다.
  `--no-inline` 을 준 호출에서도 같은 문구를 쓴다.

  **제외한 본문 참조의 수는 적지 않는다.** `--no-inline` 은 본문을 받지 않는 선택이라
  그 수를 셀 근거가 없다. 세려면 제외하기로 한 본문을 다시 받아야 하고,
  그것은 옵션이 아끼려던 왕복을 되살린다.
  `--no-inline` 을 준 쪽은 본문을 제외한다는 것을 이미 알고 부른다.

- **맥락**: `download-all` 은 `getPostFiles` 결과만 대상으로 삼았다.
  본문에 이미지를 붙여 넣은 업무는 첨부 목록이 비어 있어 `첨부파일이 없습니다` 로 끝난다.
  그 업무에 이미지가 두 장 있어도 출력은 없다고 말한다.

  결함 보고처럼 재현 화면을 본문에 붙여 넣는 업무에서 이 형태가 흔하다.
  이미지가 유일한 증거인 업무도 있어, 증거를 모으는 자동화가 통째로 놓치고 놓친 사실도 드러나지 않는다.

  같은 파일을 `post file download --file-id <id>` 로는 받을 수 있다.
  본문에서 id 를 뽑는 일만 호출하는 쪽이 매번 다시 만들고 있었다.

- **대안 기각**:
  - **`--include-inline` 옵션을 줄 때만 받는다** — 기본 동작이 명령 이름과 어긋난 채로 남는다.
    `download-all` 을 부르는 쪽은 그 업무의 파일을 다 받으려는 것이고, 옵션의 존재를 알아야만 그렇게 되는 것은 발견하기 어렵다.
    실제로 이 문제를 보고한 쪽도 옵션이 아니라 사실과 다른 안내를 문제로 짚었다.
  - **안내만 고치고 받지는 않는다** — 본문에 이미지가 몇 장 있는지 알려 주어도 받는 일은 호출하는 쪽에 남는다.
  - **본문 파일을 별도 명령으로 나눈다** — 사용자는 어느 파일이 첨부이고 어느 파일이 본문에 있는지 구별하지 않는다.
    나누면 두 명령을 모두 불러야 그 업무의 파일을 다 받는다.

- **결과**:
  - 얻는 것: 본문에만 이미지가 있는 업무에서도 `download-all` 이 그 파일을 받는다.
    받을 것이 없다는 안내가 사실과 맞는다.
    본문에서 id 를 뽑는 코드를 호출하는 쪽마다 다시 만들지 않는다.
  - 감당할 것: 같은 명령이 종전보다 많은 파일을 받는다.
    받은 파일 수를 세거나 디렉터리를 그대로 비교하던 자동화는 결과가 달라진다. `--no-inline` 이 그 경로를 남긴다.
    본문 파싱이 정규식이라 코드 블록 안의 `/files/<id>` 문자열도 대상이 된다.
    받아서 손해가 나지 않는 쪽이라 구별하지 않는다.
    본문 참조 중 접근 권한이 없거나 이미 삭제된 id 는 내려받기가 실패한다.
    기존 부분 실패 처리(`failed` 배열과 종료 코드 1)를 그대로 쓴다.

- **적용 범위**: `src/commands/post/file/download-all.ts` 와 본문에서 파일 id 를 뽑는 새 유틸리티.
  `--json` 출력 스키마는 [ADR-031](031-file-json-output-schema.md) 이 정한 `{ count, succeeded, failed }` 를 그대로 쓴다.
