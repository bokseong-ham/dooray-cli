# plan071 검토 지적 (판정: REJECT)

이 plan 을 이슈 #164 와 대조한 결과다.
**구현을 시작하기 전에 아래를 plan 에 반영하고, 반영한 것을 커밋으로 남긴다.**

그대로 실행하면 기존 테스트가 깨진 채로 검증 절을 통과하지 못한다.

## Critical

### C1. `src/api/imapClient.test.ts` 가 이미 있고 phase-01 의 변경으로 여러 건이 실패한다

`phase-01.md:123` 은 「이 파일이 없으면 만든다」라고 적지만
그 파일은 466줄로 이미 있고 `resolveUidByMailId` 확인을 여럿 담고 있다.
아래가 phase-01 의 변경으로 깨진다.

| 확인 | 깨지는 이유 |
| --- | --- |
| `정확히 한 후보면 UID 를 반환한다` | `toHaveBeenCalledWith({ all: true }, { uid: true })` 와 `fetchOne` 호출을 단언한다 |
| `4000통 입력에서 fetchOne 조회는 로그 수준에 머문다` | `fetch` 첫 호출의 UID 개수가 17 이하라고 단언한다. 일자 필터에는 그 창이 없다 |
| `초 경계를 넘은 도착 시각과 문자열 날짜를 처리한다` | `fetchOne` 호출 인자를 단언한다 |
| `조회 범위 끝의 단일 후보 뒤에 같은 초의 메일이 더 있으면 선택하지 않는다` | phase-01 이 지우기로 한 그 분기를 검사한다 |
| `불완전한 날짜` 갈래 | `fetchOne.mockResolvedValue(false)` 로 오류를 만든다. 그 경로가 사라지면 오류가 나오지 않는다 |
| `검색 UID가 역순이고 사이 번호가 비어도...` | 이분 탐색 전제로 짜인 데이터다. 재검토가 필요하다 |

`phase-01.md:143` 의 검증은 `pnpm test` 종료 코드 0 을 요구하는데
작업 항목에 이 확인들을 고치라는 지시가 없다.

**고칠 것**: 작업 항목 4 를 「기존 확인 중 이분 탐색을 전제한 것을 나열하고 각각 삭제·재작성한다」로 바꾸고
위 표의 확인 이름을 phase 에 적는다. 줄 번호는 파일을 열어 그때 값으로 적는다.

### C2. 「하루 도착량이 많은 사서함」의 동작이 정의되어 있지 않다

이슈 #164 는 「하루에 도착하는 메일이 많으면 후보가 그대로 많이 남아 개선폭이 크지 않을 수 있다」를
이 변경의 핵심 위험으로 적는다.
`phase-01.md:101-120` 의 작업 항목 3 은 이 위험을 UID 문자열 길이 문제로만 다룬다.

후보가 15000건이면 `fetchMailIdCandidates` 호출이 `ceil(15000/500) = 30` 회가 되어 왕복이 31회다.
현재 구현의 14회보다 나쁘다. envelope 을 15000건 내려받는 전송량도 더해진다.
그 경우 이분 탐색으로 되돌리는지, 오류로 멈추는지, 그대로 진행하는지가 어디에도 없다.

**ADR 쪽은 이미 고쳤다.** `docs/adr/040-mail-url-to-uid-lookup.md` 의 보강 절이
후보 수 상한을 두고, 넘으면 UID 를 고르지 않고 중단해 `mail list --search` 를 안내한다고 정한다.
왕복 수가 `1 + ceil(후보수 / 배치크기)` 라는 것도 적는다.

**고칠 것**: 상한값을 정하고 그 판단을 작업 항목 3 에 명시한다.
되돌릴 방식을 남기려면 이분 탐색 코드를 지우지 말아야 하므로 작업 항목 2 와 함께 정한다.

## Major

### M1. `임계값` 이 정의되어 있지 않다

`phase-01.md:109` 는 「후보 수가 임계값을 넘으면 범위를 순차 조회로 나눈다」고 적고
`MAIL_ID_FETCH_BATCH = 500` 만 준다.
500 이 임계값인지 배치 크기인지, 임계값 이하일 때 기존 한 번 호출을 쓰는지가 갈린다.
이어지는 `:115` 는 조건 없이 항상 자르는 것으로 읽힌다. 두 해석이 충돌한다.

**고칠 것**: 배치 크기와 상한을 다른 이름으로 나누고 각각의 뜻을 적는다.

### M2. phase-01 과 phase-02 가 `MAIL_ID_SEARCH_TIME_MARGIN_MS` 를 두고 어긋난다

`phase-01.md:59` 는 「후보 판정에 쓰이는지 확인하고, 쓰이지 않으면 함께 지운다」고 적는다.
그 상수는 `src/api/imapClient.ts` 한 곳에서만 쓰이고 그 줄은 이분 탐색 비교문이라
phase-01 작업 항목 2 가 지운다. `isCandidateMatch` 는 그 상수를 쓰지 않는다.
따라서 반드시 삭제된다.

그런데 `phase-02.md:47` 은 「`MAIL_ID_SEARCH_TIME_MARGIN_MS` 위의 주석이 여기 해당한다」며
그 상수가 남아 있는 것을 전제한다. 실행자는 없는 상수를 찾게 된다.

**고칠 것**: phase-02 의 그 문장을 지우거나 다른 자리를 가리킨다.

### M3. phase-02 의 작업 항목이 `CLAUDE.md` 를 다루지 않는데 검증은 그것을 검사한다

`CLAUDE.md` 의 mail 계열 규약이 「mail id 는 도착 시각으로 풀어 UID 를 이분 탐색한다 (ADR-040)」를 적는다.
`phase-02.md:85` 의 검증 명령은 `CLAUDE.md` 를 대상에 넣어 결과가 0 이어야 한다고 요구하지만
작업 항목과 Critical Files 표에 `CLAUDE.md` 가 없다. 검증이 반드시 실패한다.

**고칠 것**: 작업 항목과 Critical Files 에 `CLAUDE.md` 를 더한다.

### M4. 조회 범위가 앞뒤 하루가 아니라 UTC 사흘이다

`phase-01.md:39` 와 `:55` 는 「앞뒤 하루씩을 받는다」고 적고
테스트 기대(`:128`)도 「두 값의 차이가 이틀」로 둔다. 실제 동작은 다르다.

- `node_modules/imapflow/lib/search-compiler.js` 의 `processDateField` 가
  `BEFORE` 에 넘긴 Date 의 UTC 시각이 `00:00:00.000Z` 가 아니면 하루를 더한다
- 같은 라이브러리의 `formatDate` 가 `toISOString()` 을 써 UTC 일자로 만든다

그래서 실제 질의는 `SINCE (대상일-1) BEFORE (대상일+2)` 이고
받는 범위는 `대상일-1`, `대상일`, `대상일+1` 의 UTC 사흘이다.

범위가 충분한지는 문제가 아니다. 서버의 시간대가 어긋나도 그 폭이 흡수한다.
문제는 후보 수다. **C2 의 위험 크기가 phase 가 가정한 것의 약 세 배다.**

**ADR 쪽은 이미 고쳤다.** 보강 절이 그 동작과 UTC 기준을 적는다.

**고칠 것**: 의도 메모에 그 두 가지를 적는다.
그래야 다음 사람이 범위를 줄이려다 상한 쪽이 실제로 이틀이라는 것을 모르고 자르지 않는다.
테스트 기대값도 이틀이 아니라 실제 값으로 고친다.

### M5. 기존 mock 구조로는 테스트 표가 요구하는 것을 확인할 수 없다

`src/api/imapClient.test.ts` 의 가짜 `search` 는 질의를 무시하고 항상 전체 UID 를 돌려준다.
`phase-01.md:128-129` 가 요구하는 「질의 형태」와 「후보 10통일 때 왕복 2회」를 그 mock 으로 검사하면
일자 필터가 실제로 후보를 좁히는지는 검사되지 않는다.
4000통 확인도 그대로 두면 `fetch` 한 번에 4000 UID 가 들어가 통과해 버린다.

**고칠 것**: 가짜 `search` 가 `since`/`before` 를 읽어 걸러내도록 고치라는 지시를 작업 항목 4 에 넣는다.

### M6. 성능 측정을 재현하는 방법이 phase 에 없다

이슈는 현재 구현과 일자 필터의 왕복 횟수와 전체 처리 시간을 측정해 비교하라고 적는다.
`phase-01.md:167-175` 의 검증은 변경 뒤의 전체 처리 시간만 `time` 으로 재고
왕복 횟수와 후보 수를 어떻게 세는지는 적지 않는다.
통과 조건도 쓸 수 없다. 「135ms 부터 252ms 에 연결과 로그인 시간이 더해진다」는
더해지는 값이 얼마인지 모르므로 판정 기준이 되지 않는다.

**고칠 것**: 왕복 횟수를 세는 방법과 측정 절차를 적고,
합격 기준을 「왕복 2회」처럼 셀 수 있는 값으로 바꾼다.
